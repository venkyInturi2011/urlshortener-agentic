# Testing approach

Two systems are tested, and the second one is tested *by the first*:

1. **The orchestrator** – conventional automated tests (JUnit 5 + AssertJ), deterministic, no network.
2. **The generated service** – its own tests are generated by the tester agents, then **executed by the orchestrator
   as an exit gate** (`mvn compile`, `mvn test`). A defect in a template therefore fails a workflow run instead of
   silently shipping (this happened twice; see [ENGINEERING_SUMMARY](ENGINEERING_SUMMARY.md)).

```bash
mvn clean verify                       # orchestrator: 111 tests + JaCoCo gate (line coverage >= 85 %)
cd shortener-service && mvn verify     # the committed greenfield output: 71 tests
bash scripts/run-all.sh                # all three scenarios end to end, building/testing each generated version
```

## 1. Orchestrator – 111 tests, 97.3 % line / 88.9 % branch coverage

| Test class | Tests | What it proves |
|---|---|---|
| `WorkflowGraphTest` | 6 | layers, joins, cycle/unknown/duplicate detection, **data-flow dirty closure**, Mermaid |
| `WorkflowEngineTest` | 25 | see below |
| `AuditLogTest` | 7 | chain verifies; **edit, delete, reorder** detected; reopen continues chain; 8 concurrent writers → valid chain of 200 |
| `PolicyTest` | 19 | each security/compliance/change-control rule blocks; test code is WARN only; path escape variants; dependency allow-list; classifier tiers and reasons |
| `ValidatorsTest` | 10 | Java brace checker ignores strings/comments/text blocks; broken Java/XML (incl. XXE-style DOCTYPE)/JSON/YAML rejected; OpenAPI and docs gates; Maven skip is reported as *not executed* |
| `ResilienceTest` | 8 | snapshot restore/delete, reverse-order committed rollback, persistence/reload, safe-stop latch and kill file, fault-spec parsing and one-shot semantics |
| `AgentsTest` | 19 | requirement extraction, ambiguity flagging (and *not* flagging when explicit), answer refinement; architect/OpenAPI content; risk, review, template rendering, fallback ignores parameters; impact analysis on a synthetic codebase; docs/changelog; release verdict matrix |
| `SupportTest` | 6 | context versioning/dedupe/persistence, metrics maths (success rates, MTTR, counters), approval gates incl. fail-closed console |
| `ScenarioRunsTest` | 9 | **the three real scenarios chained** end to end; brownfield recovery from injected bad output; halt when primary+fallback fail; denied approval; CLI run / verify-audit / tamper → exit 3 / copy-from / inject / **resume**; bad usage; every shipped scenario is a valid graph referencing known agents and validators |
| `TemplateIntegrityTest` | 2 | every template file is indexed and vice versa (13 change sets); only known placeholders |

`WorkflowEngineTest` scenarios, each with fake or fault-injecting agents and temp directories:

* parallelism: two sibling nodes must be running simultaneously (latch) and the join must not start early
* transient failure → retried; retries are bounded; global attempt budget enforced inside the retry loop
* exit-gate failure → file exists during gate → **rolled back** → retry succeeds; rollback restores a pre-existing file
* fallback agent takes over after primary exhausts retries; total failure → **safe-stop**, downstream `SKIPPED`
* policy violation is **fatal, not retried, nothing written**
* human gate: denial halts the run and writes nothing; approval is audited; HIGH-impact edit of an existing `pom.xml`
  triggers approval *without* a gate; LOW-impact needs none
* entry gate (missing input), kill-switch file, provenance header on generated Java
* fault injection: exception recovered by retry, bad output caught by `structure` gate and rolled back, policy fault
  halts, primary+fallback fault halts
* **resume** after halt does not repeat completed work and keeps the audit chain valid
* **re-planning**: only the consumers of the changed artifact re-run (`a`,`c` twice; `b` once), files from the
  superseded run are replaced, a no-op clarification causes no re-plan, unknown event type is rejected

Design choices that keep the suite fast and reliable: no sleeps beyond 1 ms backoff, temp dirs per test, Maven builds
disabled by `--skip-build` (the validator reports *skipped*, and the release agent downgrades to CONDITIONAL – itself
asserted), the full suite runs in ~10 s.

Not covered by unit tests (by design or lack of time): `MavenValidator` happy path (needs a real project – covered
by the scenario runs), the `Main.main` `System.exit` wrapper, console-interactive wiring under a real TTY,
time-dependent behaviour beyond coarse bounds (MTTR is asserted ≥ 0, not an exact value).

## 3. Validation layers (defence in depth)

| Layer | When | Catches |
|---|---|---|
| Graph validation | scenario load | cycles, unknown/duplicate nodes |
| Entry gate | before a node starts | missing upstream artifacts |
| Policy engine | before anything is written | secrets, command exec, SQL concatenation, PII logging, path escape, unapproved dependencies |
| Human approval | before apply, for gates and HIGH-impact changes | wrong direction, risky contract/schema change |
| `structure` | after apply | unbalanced Java, malformed XML/YAML/JSON, empty files |
| `mvn compile` / `mvn test` | at joins | cross-module incompatibilities, behavioural regressions |
| Release assessment | last node | tests not executed, open ambiguities, policy blocks, broken audit chain |
| `verify-audit` | any time | tampering with the run history |

## 4. Known testing gaps

* No load/performance tests (the p95 target in the ambiguous scenario is an assumption, not a measured result).
* No mutation testing; no property-based testing of the SSRF validator (the parameterised list is hand-chosen).
* No contract test comparing generated OpenAPI with the implemented controllers – today they are generated from the
  same requirement artifact and checked for plausibility, not machine-verified for equivalence.
* A GitHub Actions workflow (`.github/workflows/ci.yml`) is provided but has not been executed in this environment.
